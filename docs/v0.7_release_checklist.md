# v0.7 Docker release checklist

This is a release-review aid, not a second source of backlog truth. `TODO.md`
owns release accounting; each state below names the evidence boundary.

## PROVEN

- Kilted amd64 and Lyrical amd64 production build/runtime contracts.
- Kilted/Lyrical arm64 BuildKit/QEMU packaging and smoke (emulated only).
- Native Kilted arm64 build and inspected runtime on a physical Raspberry Pi,
  including no-device lifecycle and live least-privilege UM982 serial ingestion.
- Real-robot Kilted arm64 runtime with selected u-blox-only mapping, advancing
  valid fix, protected runtime-only NTRIP, valid RTCM forwarding/correction
  health, clean stop/device release, and exact legacy GPS restoration.
- Stable by-id, non-root, no-privileged serial-device policy.
- External NTRIP configuration and credentials outside the image.
- tini entrypoint, `SIGINT` stop contract, and bounded component-response
  healthcheck proven in the current Kilted image.
- Standard OCI identity, runtime diagnostic identity, immutable-tag rollback,
  and SBOM/provenance release-artifact plan.
- Same-host Docker bridge DDS/domain-isolation evidence.
- Physical robot/second-RPi DDS discovery and payload in both directions plus
  different-domain non-delivery, using the recorded explicit bridge/unicast
  contract. Unmodified bridge multicast failed and is not claimed.
- Robot lifecycle matrix: clean stop/start, unexpected main launch-process
  exit with `unless-stopped` recovery, Docker daemon restart, and host
  reboot/autostart each restored the exact external configuration and fresh
  healthy GNSS under the sole by-id device grant.
- Robot USB identity matrix: the selected u-blox retained its stable by-id
  while changing from `ttyACM1` / 166:1 to `ttyACM2` / 166:2; its existing
  container stayed GNSS-stale until recreation. Deliberate UM982 substitution
  then made the exact u-blox-by-id-pinned startup fail explicitly without
  opening the wrong receiver, and both receivers recovered under their original
  stable identities. The swap's UM982 USB power loss required the established
  14-command runtime-only profile replay; no persistent/reset command ran.
- Local non-secret support snapshot tool, external logs, and bounded retention
  guidance.
- External log and support-export mounts validated as writable by numeric
  UID/GID `1000:1000`, persistent across container recreation, and free of
  supplied credential values. The snapshot tool is installed in the image.
- Stable non-colored ROS console envelopes with timestamp, severity, logger,
  and message fields; Docker Compose retains bounded `local` driver rotation.
- Hardware-free Docker DNS/NTRIP recovery: one unchanged client container
  re-resolved a previously absent network alias, streamed valid RTCM from a
  local fake caster, detected caster loss, and streamed again from a new caster
  incarnation under the same alias.
- Bounded no-device behavior in the exact current Kilted image: Docker health
  stayed healthy because both enabled nodes answered bounded Trigger requests,
  while receiver discovery was ERROR, observation sequence was zero, fix/RTK/
  corrections were false, NTRIP was reconnecting, and forwarded RTCM was zero.

## PARTIAL

- USB-loss contract: selected stable identity must be re-resolved and the
  container recreated. The u-blox needed no provisioning replay; the UM982
  runtime-only profile must still be replayed after USB power loss. This is not
  transparent hotplug recovery or an old-incarnation byte cutoff.
- Live u-blox/Unicore GNSS, NTRIP, RTCM, and RTK Float evidence. RTK Fixed and
  the remaining receiver/NTRIP/incarnation matrix remain separate.
- Receiver-child recovery failed on the previously validated robot image. The
  exact current local Kilted image now proves the software policy: receiver
  SIGKILL terminated the launch and its NTRIP peer, `unless-stopped` incremented
  the restart count, recreated both children, issued a new receiver incarnation,
  and exposed no fresh cached observation or correction state. Physical
  receiver validation remains pending. Explicit operator
  `docker kill` also remained stopped with exit 137/restart count 0 and is not
  treated as process-crash or reboot evidence.

## Open-gate dependency accounting

The generated development-status dependency panel is derived from the versioned
`release_gate_dependencies` mapping in
[`docs/status/uga_backlog.json`](status/uga_backlog.json), not from UGA finding
validation labels or checkpoint prose. Every unchecked task in the fixed 65-item
v0.7 scope has exactly one exclusive classification. This preserves the
completion denominator while independently describing what acceptance evidence
is still needed.

`Open hardware-dependent gates` is a derived, non-additive grouping of native
arm64, receiver-hardware, USB-action, power-cycle, robot, and long-duration
classifications. Do not add that aggregate to the exclusive category counts.
External-LAN DDS is a separate completed physical-topology acceptance matrix, not
one of the 65 checklist tasks; its evidence remains tracked in the deployment
checkpoint and does not inflate this panel's release-gate total.

## Operator limits

- Docker health proves bounded responsiveness of enabled ROS components. Use
  ROS diagnostics/snapshot for transport, freshness, fix, NTRIP, RTCM,
  correction semantics, and RTK.
- Never attach a transient tty, mount broad `/dev`, use `--privileged`, claim
  automatic hotplug recovery, or silently substitute a receiver.
